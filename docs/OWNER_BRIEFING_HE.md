# תדריך בעלים ל־7ya.io

המטרה של המסמך הזה היא להפוך את מה שנעשה באתר לשפה פשוטה: מה ניסית לבנות, איפה זה עומד, ומה עושים עכשיו בלי להסתבך בקוד.

## מה קרה בחודשיים האחרונים

מהיסטוריית העבודה בריפו עולה שניסית להפוך את `7ya.io` מאוסף קבצים/ניסויים לאתר ציבורי מסודר סביב איגור ופרצקי ו־7YA.

בפועל נבנו כמה שכבות:

1. **אתר ציבורי סטטי ויציב** — עמוד הבית, עמוד איגור, Talk, Evidence, StartOn, Social, Contact, Radar, Pass ומפת אתר.
2. **זהות ומסרים** — מעבר ממבנה כללי של “ניהול” לבית ציבורי ברור: מי זה איגור, מה זה 7YA, ומה המבקר צריך לעשות עכשיו.
3. **שכבת הוכחות וזהירות** — התחלה של Evidence ו־Evidence Oracle כדי להפריד בין טענות מאומתות, טיוטות, ורעיונות שעדיין דורשים מקור.
4. **שכבת פרסום ופריסה** — ניסיונות סביב Vercel, Netlify, בדיקות נתיבים, health checks ופקודות אימות.
5. **שכבת מוצר עתידית** — Member Pass, Radar, Social Signal Wall, Visual AI Lab, API health, ותחילת שכבת PostgreSQL ל־Netlify Functions.

## המצב כרגע בשפה פשוטה

האתר כרגע צריך להישאר **פשוט, ציבורי, ואמין**.

זה אומר:

- עמוד הבית לא צריך להסביר הכול.
- כל דבר שלא בטוחים בו צריך לעבור דרך Evidence או להישאר מנוסח כטיוטה.
- Talk הוא שער הכניסה לאנשים שרוצים לדבר, לשתף פעולה, לשלוח רעיון או לבקש עבודה.
- StartOn הוא כרגע מסלול השפעה חברתית, לא טענה משפטית/מוסדית מוגמרת.
- Member Pass ו־API הם שכבות עתידיות/טכניות, לא הדבר הראשון שמבקר צריך להבין.

## מה לא לעשות עכשיו

כדי לא לשבור את האתר ולא להעמיס עליו:

- לא להוסיף מספרים גדולים, תארים, חסויות או הישגים בלי מקור גלוי.
- לא להפוך את עמוד הבית לדשבורד עמוס.
- לא לערבב בין 7YA, StartOn, Talk, Evidence ו־Member Pass כאילו כולם אותו מוצר.
- לא למחוק בדיקות רק כי הן מפריעות; אם בדיקה נכשלת, צריך להבין אם היא מגנה על האתר.
- לא להוסיף סודות, מפתחות API או פרטי גישה לקבצים ציבוריים.

## סדר הפעולות המומלץ

### שלב 1 — להשאיר את האתר חי וברור

המטרה: שכל מבקר יבין תוך 10 שניות לאן הגיע.

בדיקות לפני שינוי גדול:

```bash
npm run check-site
npm run check-links
```

אם שתי הפקודות עוברות, הבסיס הציבורי תקין.

### שלב 2 — להחליט מה המסר הראשי

המסר הנוכחי:

> 7YA הוא הבית הציבורי סביב Igor Vepretski — מדיה, מערכות, הוכחות, ודלת כניסה לשיחה.

אם זה עדיין נכון, לא צריך להחליף את כל האתר. צריך רק לשפר מסלולים קטנים.

### שלב 3 — להפריד בין “חי עכשיו” לבין “בבנייה”

חי עכשיו:

- `/`
- `/igor-vepretski/`
- `/talk/`
- `/evidence/`
- `/starton/`
- `/social/`
- `/contact/`
- `/radar/`
- `/pass/`

בבנייה או טכני יותר:

- Netlify Functions
- PostgreSQL
- Admin
- Payments
- Evidence Oracle
- Member Pass wallet
- Visual AI Lab

### שלב 4 — כל שינוי חדש צריך לענות על שאלה אחת

לפני שמוסיפים עמוד/פיצ׳ר, לשאול:

1. האם זה מסביר מי זה איגור?
2. האם זה מסביר למה 7YA קיים?
3. האם זה מגדיל אמון?
4. האם זה נותן למבקר פעולה ברורה?

אם התשובה היא “לא”, עדיף לא להוסיף את זה לעמוד הבית.

## מפת קבצים שימושית

- `index.html` — עמוד הבית הציבורי.
- `igor-vepretski/index.html` — עמוד הזהות של איגור.
- `talk/index.html` — שער השיחה והפנייה.
- `evidence/index.html` — אזור הוכחות וזהירות בטענות.
- `starton/index.html` — מסלול ההשפעה החברתית.
- `social/index.html` — קיר הסיגנלים החברתיים.
- `docs/my-links.md` — מפת קישורים ציבורית.
- `scripts/check-site.mjs` — בדיקת בריאות לאתר הציבורי.
- `scripts/check-links.mjs` — בדיקת קישורים פנימיים בעמודי HTML.
- `netlify/functions/` — שכבת API עתידית/טכנית.
- `packages/evidence-oracle/` — לוגיקת אימות ראיות.

## בקשה טובה ל־AI בפעם הבאה

אפשר להשתמש בטקסט הזה כמו שהוא:

> תעבוד על 7ya.io בזהירות. קודם תריץ `git status`, תקרא את `README.md`, `docs/OWNER_BRIEFING_HE.md`, `scripts/check-site.mjs`, ו־`scripts/check-links.mjs`. אל תוסיף טענות לא מאומתות. אם אתה משנה את האתר הציבורי, תריץ `npm run check-site` ו־`npm run check-links`. המטרה היא להשאיר את האתר פשוט: Igor → 7YA → Talk → Evidence.

## החלטה ניהולית קצרה

הכיוון הנכון עכשיו הוא לא “עוד פיצ׳רים”. הכיוון הוא **לייצב את הסיפור**:

- מי אתה.
- מה 7YA.
- למה זה אמין.
- איך יוצרים קשר.

אחרי שזה יציב, אפשר לחזור ל־API, Member Pass, תשלומים, ואדמין.
